# Одна работа в двух языковых версиях: состояние 4 октября 2026

Рабочее название: **«Ресурсная эффективность локальных языковых моделей в аграрных задачах: сравнение конфигураций 9B и 27B и использование расчётных инструментов»**. EN: *Resource-Efficient Local Language Models for Agricultural Tasks: A 9B–27B Comparison with Deterministic Tools*. Это один эмпирический development case study; RU/EN не являются независимыми статьями.

Антоний прямо принял порядок авторов **Antoniy Sarychev / Антоний Сарычев**, затем **Denis Shesternin / Денис Шестернин**, фокус на local quality/latency/memory/reliability/reproducibility, Qwen3.5-9B как практическую конфигурацию и Qwen3.8-27B как reference с более высоким наблюдаемым качеством. MERA public DEV остаётся основным knowledge benchmark, Study C — отдельным техническим опытом с формулами/единицами/входами. Mercury direct — supplementary cloud reference; CLI — продуктовые harness comparisons. Рукопись продолжается без ожидания MERA. Это решения Антония; окончательное одобрение конкретного текста, вкладов и лицензии обоими авторами, включая Дениса, ещё требуется. Анастасия по предоставленному контексту — преподаватель, без автоматического соавторства или назначения руководителем.

## Что изменил аудит и какие выводы допустимы

Повторное offline scoring подтвердило все293 per-item метрики обеих моделей, raw/source hashes, paired counts **113both/28only9/37only27/111neither** и historical domain-stratified bootstrap10000/seed20261003: EM9−EM27 **−3,1142п.п.**, descriptive95% **[−8,3045;+2,4221]п.п.**. Reference IDs **222,300,317,374** остаются unresolved; основной denominator289. **141/293 и150/293** — отдельная консервативная sensitivity, не gold correction. «94% observed EM27» — ratio141/150, не accuracy94% или equivalence.

DEV60 полностью включён в DEV293; TELEMETRY40 тоже subset и пересекается с DEV60 по20ID. Screening/model selection и repeated development evaluations раскрыты; ни один из них не превращается в независимый confirmatory holdout. HOME150, MERA, TELEMETRY40 и Study C имеют разные конструкции и не объединяются в одну accuracy.

Actual UTF-8 system/user inputs80пар совпали, saved weight receipts совпали, но native runtime изменяет seed/schema/checkpoints/GPUplacement. Parsed answers изменились1/40 Q9 и2/40 Q27. Поэтому нельзя приписать historical141/289 и150/289 одновременно измеренной native speed. Можно совместно показать **собственное native40 качество22/39 и24/39** и его timing — отдельный retrospective compatibility block. HistoricalDEV293 сохраняет собственную таблицу. Это практические конфигурации разных generations/quantization/offload, а не causal size study; numeric non-inferiority margin не задавалась.

Native40 sampled request peaks: whole GPU **11471/13287MiB**, whole-system RAM **20,8581/28,4704GiB**; named process-group RSS — отдельная scope. Requested GPU ratio не measured layer count; private allocation/energy не измерены. Short answer-letter/JSON timing не доказывает long-form speed. Native API не раскрывает точный EOS/length reason.
