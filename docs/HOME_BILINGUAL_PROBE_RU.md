## Как интерпретировать дальнейший запуск

Запуск выбранного GPT-OSS должен использовать тот же SYSTEM_PROMPT, явно записанный model artifact/quantization, context 4096, parallel=1, reasoning=off и последовательное выполнение. Через текущий LM Studio CLI temperature, seed, max tokens и принудительный JSON grammar полностью не контролируются: сохранять UNKNOWN и диагностический статус, а не объявлять frozen API experiment. Весовой файл и предыдущие результаты остаются неизменными.

Первую inference после load сохранять как видимый cold/warmup request; не исключать её из latency задним числом. Сам CLI subprocess запускается заново для каждого запроса, тогда как модель остаётся загруженной. Файл располагает EN затем RU внутри каждой пары; это создаёт потенциальную зависимость языка и порядка для latency/cache. При сравнении времени явно раскрыть порядок либо **до начала** выполнить заранее документированное чередование EN-first/RU-first по pair index. При шести парах вывод о language latency всё равно описательный.

Отчёт должен показывать EN и RU correctness из 6, paired transitions (оба верны / только EN / только RU / оба неверны), EM и F1 отдельно, JSON failures, wall latency и provider tok/s/TTFT при наличии. Не объявлять 12 records независимыми observations: статистическая единица — source pair/group. На шести groups интервал нестабилен; модель уже выбрана по DEV, перевод не имеет human validation, поэтому нельзя утверждать подтверждённую русскоязычную generalization, noninferiority или превосходство.

Лексическая метрика может штрафовать русское склонение, кавычки и другое корректное название руководства. Сохранить outputs и отдельно пометить случаи для ручного аудита; gold и scoring после просмотра ответов не менять. Облачная и hybrid части этим probe не выполняются. Фактические результаты будущего запуска должны храниться в новой timestamped директории, с этим dataset SHA256 и меткой development bilingual diagnostic.
