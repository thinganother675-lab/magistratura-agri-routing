# Следующий исследовательский этап: A / B / C

3 октября 2026. Этот документ задаёт новое направление и заменяет требование
заполнить review40 как основной агрономический эталон следующего эксперимента.
Предыдущие протоколы, результаты и формы сохраняются как исторические версии.

| Исследование | Назначение | Статус |
|---|---|---|
| A — HOME150 | Контролируемый исторический случай: инструменты, ресурсы, составной проверяющий механизм | Заморожено; никаких замен чисел, повторного сбора или смешивания с MERA |
| B — ruTXTAgroBench | Профессиональные русскоязычные знания по готовым эталонам специалистов | Новая серия; малый DEV-прогон; закрытый TEST пока запрещён научным шлюзом и указанием о внешних отправках |
| C — вычисления | Формулы, единицы, достаточность данных, явно типизированный выбор инструмента | Отдельные 27 разработческих случаев; внешние контрольные примеры FAO; модельный эксперимент пока не выполнен |

Антоний и Денис — магистранты по компьютерным наукам/ИИ. Они проверяют реализацию,
методику, происхождение данных и допустимость выводов. Ни один не объявляется
независимым агрономическим экспертом. Экспертное происхождение MERA принимается
в пределах опубликованной методики, с её ограничениями.

## Вопросы исследования

Предлагаемая общая формулировка: может ли система выбора между локальной моделью,
облачной моделью и вычислительными инструментами сократить удалённую генерацию,
сохраняя качество на проверенных русскоязычных сельскохозяйственных заданиях?

- RQ1: как отличаются локальная и облачная модели на агрономических заданиях MERA?
- RQ2: какой компромисс качества и числа облачных запросов даёт заранее выбранный каскад?
- RQ3: какие численные ошибки и обращения к облаку устраняет применение явных формул?

RQ1/RQ2 относятся к B, RQ3 — к C. Множественный выбор сам по себе не измеряет
выбор вычислительного инструмента. Средний показатель по объединённым B+C не
создаётся. Jev пока не включён в основной новый эксперимент: он расширил бы
сравнение и добавил собственные внешние запросы без подтверждённой необходимости.
Если его вернут, все запросы маршрутизатора учитываются отдельно от генерации.

## Протокол B и ограничения

Первичная будущая пара — один локально-облаччный каскад против одной облачной
модели. LOCAL ONLY нужен для RQ1 и объяснения каскада. Не перебираем множество
систем на скрытом TEST. Подбор локальной модели, инструкции, нормализатора и
правила выполняется только на DEV. Все 293 открытых задания относятся к разработке;
внутреннее разделение или отложенная часть DEV не превращают их в официальный TEST.

На первом этапе используется фиксированная подборка 60 DEV: по шесть заданий
каждой дисциплины, отбор по ID без эталона. Общий промпт — исходная инструкция
каждой строки, без дополнительных примеров. Технические параметры и цены
записаны до вызовов в `dev_protocol_before_calls.json` новой серии.

Сигналы маршрутизации доступны при выполнении: допустимые варианты ответа,
ошибка формата, реальные logprob выбранных букв при их наличии. Вероятность
токена означает уверенность модели в записи буквы, а не вероятность
агрономической правильности. Нельзя подставлять «уверенность», когда API её не
вернул. В таком случае правило с порогом направляет запрос в облако.
Обучение модели-маршрутизатора на MERA не выполняется: соглашение запрещает
обучение моделей; для такого использования требуется отдельное разрешение.

Исходный ответ и форматная нормализация сохраняются отдельно. Нормализатор
упорядочивает/разделяет уже выбранные буквы или выделяет однозначное начальное
поле «Ответ:»; он не ищет правильный вариант в эталоне и не исправляет смысл.
Неоднозначная проза считается ошибкой формата. Кириллические буквы в исходном
эталоне отдельно помечены; исходные ответы специалистов не переписываются.

**Опубликованный SQuAD-проверяющий код удаляет вариант A как артикль.** До
разъяснения версии и поведения сервера совместимые EM/F1 остаются диагностикой
совместимости, а не достаточным основанием научного вывода. Дополнительная строгая
проверка множества вариантов помечается своим именем и не называется официальной.

## Статистический план до TEST

После устранения проблемы метрики оба автора утверждают основную метрику и
практически допустимую разницу качества. До этого итоговый протокол не заморожен.
На TEST фиксируются официальные EM/F1, разница каскад–облако, число генераций,
доля задач с облачной генерацией, доля задач с любым hosted-запросом, число всех
hosted-запросов на задачу, локальное разрешение, ошибки формата, задержка и стоимость.
Hosted-запросов на задачу может быть больше одного; это не доля в диапазоне 0–1.
Пакетная удалённая оценка отражается отдельно от генерации и маршрутизации.

Если сервис возвращает только средние оценки, результаты качества сравниваются
описательно. Парные интервалы, McNemar и утверждение о неуступании не вычисляются
без индивидуальной правильности/достаточного ответа сервиса. Неизвестная стоимость
не подменяется нулём. Токенная оценка не называется счётом провайдера.

DEV-каскады из кэшированных ответов — **моделирование по сохранённым результатам**.
Они не означают, что полный облачный screen фактически выполнил меньше вызовов.
Сумма записанных локальных/облачных задержек — оценка последовательного каскада,
а не измеренная задержка запущенной онлайн-системы.

## Консервативная процедура закрытого TEST

1. Разъяснить права и серверную метрику; проверить доступ к личному кабинету,
   поддержку одной задачи и описание каскада как системы.
2. Утвердить одну локальную модель, один стабильный облачный идентификатор,
   одно правило, параметры генерации, метрику, бюджет и статистические пределы.
3. Зафиксировать Git commit, SHA256 промптов/кода/версий и протокола до TEST.
4. Только после отдельного разрешения на внешнюю отправку выполнить один полный
   TEST для выбранных основных политик. Не смотреть скрытые эталоны; не настраивать
   правило по возвращённым оценкам; ошибки исполнения отражать как отклонения.
5. Сохранить все попытки, outputs, исходный официальный журнал, SHA256 архива,
   время и идентификатор отправки, ответ сервиса, версию MERA и окружения.
6. Получать приватный результат; не нажимать «Submit for moderation» и не
   публиковать в таблице результатов без отдельного разрешения пользователя.

Самописный упаковщик проверяет официальную схему и наличие исходного журнала,
но приёмка сервисом ещё не проверена. Оригинальный упаковщик может сохранять
вопросы в `logs_public.zip`; это ограниченный передаваемый артефакт, а не открытые
данные. В этом сеансе TEST не скачивается и внешняя отправка не выполняется.

## Новая роль review40

review40 — **внутренний экспериментальный пакет разработки методики**. CSV,
Excel и исходные вопросы сохраняются; заполненные формы не выдумываются.
Он может использоваться для демонстрации ASK/ABSTAIN, заданных арифметических
правил, сравнения русской/английской записи и разработки проверяющего кода.
Это не независимый агрономический эталон и не обязательное условие Study B.
Назначение каждой будущей ручной проверки должно быть технически ограничено.

## Структура статьи

Сейчас доказательное решение — **OPTION A**, узкий исторический HOME150 случай
с уже раскрытыми ограничениями. Целевая структура — **OPTION B**, MERA основное
исследование и HOME150/C как отдельные поддерживающие части, только после
корректной итоговой оценки B. OPTION C, две эмпирические статьи, сейчас не
обоснован: новых независимых итоговых результатов для такого разделения нет.
Обзорная учебная статья — отдельное прежнее требование, не способ разделить один
эмпирический результат ради числа публикаций.

MERA существенно улучшает происхождение будущих агрономических эталонов.
Пока выполненный DEV и технические проверки усиливают методику, но не доказывают
сохранение качества на скрытом TEST. Числа HOME150 остаются прежними.
